# โปร double digit — flow การสั่งซื้อและสิ่งที่ต้องเตรียม

สถานะ: ยังไม่เริ่มเขียนโค้ด รอไอซ์ตัดสินข้อที่อยู่ท้ายไฟล์

## สรุป: ไม่ต้องทำ add to cart

ใช้ flow เดิมได้ เพิ่มแค่ช่องกรอกโค้ดในฟอร์มสั่งซื้อ

เหตุผล

1. เรามีสินค้าเดียว ตะกร้ามีไว้ถือของหลายชิ้นที่ราคาต่างกัน เราไม่มีกรณีนั้น แพ็กทีม 5/10/20 คือจำนวนสิทธิ์ของสินค้าตัวเดิม ไม่ใช่สินค้าคนละตัว
2. หน้าสั่งซื้อรับพารามิเตอร์จาก URL อยู่แล้ว `order.html?pack=5` เปลี่ยนราคาทั้งหน้า ([order.html:875](../order.html:875)) เพิ่ม `?code=` เข้าไปแบบเดียวกันได้เลย ไม่ต้องรื้ออะไร
3. การทำตะกร้าแปลว่าต้องมี state ข้ามหน้า ต้องมี session ต้องมีที่เก็บของที่ยังไม่จ่าย ทั้งหมดนั้นคือระบบใหม่ที่ต้องดูแล โดยที่ลูกค้าไม่ได้อะไรเพิ่ม
4. งานยากจริงอยู่ที่ฝั่ง server ไม่ใช่ UI ดูหัวข้อถัดไป

## จุดที่ต้องระวังที่สุด

`verify-slip` ตรวจยอดโอนแบบนี้ ([verify-slip/index.ts:548](../supabase/functions/verify-slip/index.ts:548))

```ts
const PACK_PRICE: Record<number, string> = { 1: '499', 5: '1990', 10: '3490', 20: '5990' }
const seats     = PACK_PRICE[Number(order.pack) || 1] ? (Number(order.pack) || 1) : 1
const packPrice = PACK_PRICE[seats]
...
amountOk = Number(actualAmount) === Number(packPrice)
```

ยอดโอนต้องเท่ากับราคาแพ็กเป๊ะ ไม่ตรงคือ reject เป็น `wrong_amount` ทันที

แปลว่าวินาทีที่มีโค้ดส่วนลด สลิปราคาโปรทุกใบจะถูกปฏิเสธ จนกว่าจะแก้ตรงนี้

**ต้อง deploy `verify-slip` ให้เสร็จก่อน แล้วค่อยปล่อยหน้าเว็บ** ถ้าสลับลำดับ ลูกค้าที่โอนตามราคาโปรจะโดนปฏิเสธหมด

## สิ่งที่ต้องสร้างเตรียมไว้

### 1. ไฟล์ราคากลางไฟล์เดียว

ตอนนี้ราคาเขียนไว้สองที่ คือในหน้าเว็บกับใน `verify-slip` ถ้าเพิ่มโค้ดส่วนลดเข้าไปจะกลายเป็นสามที่ ต้องยุบเหลือแหล่งเดียวก่อน ไม่งั้นวันหนึ่งจะลดราคาหน้าเว็บแล้วลืมแก้ฝั่งตรวจสลิป

### 2. ตาราง `promo_codes`

| คอลัมน์ | ใช้ทำอะไร |
|---|---|
| `code` | ตัวพิมพ์ใหญ่ เช่น MERRY1212 |
| `discount_type` | `fixed` หรือ `percent` |
| `discount_value` | จำนวนเงินหรือเปอร์เซ็นต์ |
| `starts_at` / `ends_at` | ช่วงวัน เก็บเป็น timestamptz ตามเวลาไทย |
| `grace_hours` | ผ่อนเวลาหลังหมดเขต ค่าตั้งต้น 6 |
| `applies_to_pack` | จำกัดเฉพาะแพ็กไหน หรือ null คือทุกแพ็ก |
| `max_uses` / `used_count` | เผื่ออยากจำกัดจำนวน |
| `active` | ปิดโค้ดได้ทันทีโดยไม่ต้องลบ |

migration ใหม่ต้องมี `GRANT ... ON public.promo_codes TO anon, authenticated, service_role;` ด้วย ตามที่บันทึกไว้ใน CLAUDE.md เรื่อง Supabase enforcement 30 ต.ค. 2026

### 3. คอลัมน์เพิ่มใน `orders`

- `promo_code` text — โค้ดที่ใช้ เก็บไว้ตรวจย้อนหลังและทำรายงาน
- `ref` text — มาจาก `?ref=fbads-1212` ใช้แยกยอดตามแหล่งโฆษณา
- `expected_amount` numeric — ราคาที่ server คำนวณได้ตอนสร้างออเดอร์ เก็บไว้เทียบกับสลิป

### 4. เวลาสั่งซื้อต้องมาจาก DB

ตอนนี้ยังไม่มีการล็อกว่าออเดอร์ถูกสร้างเมื่อไหร่แบบที่ปลอมไม่ได้ ถ้าใช้เวลาจากเบราว์เซอร์ ลูกค้าตั้งนาฬิกาเครื่องตัวเองย้อนหลังแล้วใช้โค้ดที่หมดอายุไปแล้วได้

ใช้ trigger ตั้ง `created_at` ที่ฝั่ง DB แล้วตรวจช่วงวันของโค้ดจากค่านั้น

### 5. ผ่อนเวลาหลังหมดเขต

ลูกค้าโอนช้าเป็นเรื่องปกติ โดยเฉพาะคนที่กดสั่งตอนใกล้เที่ยงคืนวันสุดท้าย ให้ยอมรับสลิปต่ออีก 6 ชั่วโมงหลังโค้ดหมดอายุ ตรวจที่ server เท่านั้น ห้ามให้หน้าเว็บเป็นคนตัดสิน

### 6. รายงานต้องแยกยอดโปร

`daily-summary` และ `monthly-csv` ต้องแยกให้เห็นว่าออเดอร์ไหนใช้โค้ดอะไร มาจาก ref ไหน และยอดรวมของโปรเทียบกับยอดปกติ

## ข้อที่ brief เขียนไว้แต่ใช้กับร้านนี้ไม่ได้

brief ที่ส่งมาเขียนจากร้านที่มีตะกร้าและมีระบบสมาชิก ของเราไม่มีทั้งสองอย่าง จึงมีสามข้อที่ต้องตัดหรือเปลี่ยน

- **ข้อ 9 ใส่ 2 โค้ดในตะกร้า** เราไม่มีโค้ดประจำเดือนอยู่แล้ว และไม่มีตะกร้า ถ้าไอซ์ไม่ได้ตั้งใจจะมีโค้ดประจำเดือนด้วย ข้อนี้ตัดทิ้ง เหลือช่องเดียว
- **ข้อ 7 สมาชิกที่ล็อกอินอยู่** เราไม่มีระบบล็อกอิน ตัดทิ้ง
- **ข้อ 3 และ 5 จำสถานะคนที่กดลิงก์** ทำได้ด้วย localStorage เหมือนที่ตัวนับถอยหลังใช้คีย์ `ct_bdl` อยู่แล้ว แต่ต้องเข้าใจว่ามันกันคนไม่ให้รู้โค้ดไม่ได้จริง ใครก็ตามที่รู้โค้ดพิมพ์เองได้ (ซึ่ง brief ข้อ 8 ก็อนุญาตอยู่แล้ว) localStorage มีไว้คุมการแสดงผล ไม่ใช่มีไว้กันคน

## ที่ไอซ์ตัดสินแล้ว (11 พ.ย. 2569)

ไอซ์: *"ลดแค่ราคาซื้อเดี่ยว 499฿ ลดเหลือ 355฿ (double digit) ถ้า payday 325฿ ลดก่อนหน้าวันนั้นๆเช่น 11.11 ลดตั้งแต่วันที่ 8-12 แต่เดี๋ยวจะบอกเป็นรอบๆไปให้ตั้งแบบนี้เป็น default ก่อน คนที่เข้าผ่านลิ้งค์นี้เท่านั้นถึงจะเห็น แต่ถ้าเข้าผ่าน https://coachtarnslide.com/ เฉยๆจะไม่เห็นยกเว้นแคชมาเข้าลิ้งค์โปรมาก่อน"*

| เรื่อง | ค่าที่ตั้งไว้ |
|---|---|
| ลดเฉพาะ | แพ็ก 1 สิทธิ์เท่านั้น (`pack=1`) แพ็กทีม 5/10/20 ราคาปกติ |
| double digit | 499 ลดเหลือ **355฿** |
| payday | 499 ลดเหลือ **325฿** |
| ช่วงวัน (ค่าตั้งต้น) | ก่อนวันจริง 3 วัน ถึงหลังวันจริง 1 วัน เช่น 11.11 คือ 8 ถึง 12 พ.ย. |
| การมองเห็น | เห็นได้ทางเดียวคือกดลิงก์โปร เข้าหน้าแรกเฉยๆ เห็นราคาปกติ |
| จำสถานะ | เครื่องที่เคยกดลิงก์แล้ว เปิดหน้าแรกยังเห็นราคาโปร จนหมดเขตแล้วกลับเป็นปกติเอง |

ช่วงวันเป็นค่าตั้งต้น ไอซ์จะสั่งเป็นรอบๆ ไป ฉะนั้นช่วงวันต้องแก้ได้จากตารางในฐานข้อมูล ไม่ใช่แก้โค้ด

เพราะลดเฉพาะ `pack=1` ฝั่ง `verify-slip` จึงแตะเฉพาะกรณี seats เท่ากับ 1 แพ็กทีมใช้เส้นทางเดิมไม่เปลี่ยนเลย ซึ่งลดความเสี่ยงลงมาก

## โค้ดทั้งปี ให้ไอซ์เลือก

ไอซ์ 11 พ.ย. 2569: *"ชื่อโค้ดเปลี่ยนได้ไหมไม่เอาเหมือนกับอีกเพจ"* ชุดคำเทศกาล (FLOAT, MERRY, HELLO, LOVELY) เป็นของเพจอื่น ห้ามใช้ซ้ำ

ชุดที่เสนอใหม่ใช้คำของสินค้าเราเอง คือคำเกี่ยวกับสไลด์และงานนำเสนอ บางเดือนผูกกับจังหวะงานจริงของลูกค้าด้วย

| วัน | เดือน | ที่มาของคำ | โค้ด |
|---|---|---|---|
| 11.11 | พ.ย. | เด็คงานนำเสนอ | `DECK1111` |
| 12.12 | ธ.ค. | สไลด์ | `SLIDE1212` |
| 1.1 | ม.ค. | เริ่มต้นปีใหม่ | `START11` |
| 2.2 | ก.พ. | เล่าเรื่อง | `STORY22` |
| 3.3 | มี.ค. | กราฟข้อมูล | `CHART33` |
| 4.4 | เม.ย. | กรอบเลย์เอาต์ | `FRAME44` |
| 5.5 | พ.ค. | ธีมสี | `THEME55` |
| 6.6 | มิ.ย. | เปิดเทอม | `CLASS66` |
| 7.7 | ก.ค. | แผนภูมิ | `GRAPH77` |
| 8.8 | ส.ค. | หัวข้อสไลด์ | `TITLE88` |
| 9.9 | ก.ย. | สิ้นปีงบประมาณ | `BUDGET99` |
| 10.10 | ต.ค. | บอร์ดนำเสนอ | `BOARD1010` |

ทุกตัวสั้น พิมพ์ง่าย ไม่มีคำที่สะกดผิดได้ง่าย และไม่ซ้ำกับเพจไหน

ไอซ์อนุมัติชุดนี้แล้ว 11 พ.ย. 2569: *"เอาตามนี้"*

ลิงก์โฆษณาจะเป็น `coachtarnslide.com/dd/deck1111?ref=fbads-1111`

## payday (ตัดสินแล้ว 11 พ.ย. 2569)

ไอซ์: *"pay จะ 24- วันที่ 2 เดือนหน้า ถ้าไม่มีไรเปลี่ยนแปลงตั้งเป็น defualt"*

ช่วงวันตั้งต้น วันที่ 24 ถึงวันที่ 2 ของเดือนถัดไป ราคา 325฿ ลดเฉพาะ `pack=1` เหมือนกัน

โค้ด payday ต้องไม่ชนกับโค้ด double digit จึงใช้คำของสินค้าเราบวกตัวย่อเดือน ไม่ใช่ตัวเลข

| เดือน | โค้ด | เดือน | โค้ด |
|---|---|---|---|
| พ.ย. | `PITCHNOV` | พ.ค. | `COVERMAY` |
| ธ.ค. | `POSTERDEC` | มิ.ย. | `PLANJUN` |
| ม.ค. | `BRIEFJAN` | ก.ค. | `REPORTJUL` |
| ก.พ. | `PRINTFEB` | ส.ค. | `TIMEAUG` |
| มี.ค. | `TABLEMAR` | ก.ย. | `REVIEWSEP` |
| เม.ย. | `ICONAPR` | ต.ค. | `SUMMAOCT` |

### โปรสองตัวจะทับกันบ่อย ต้องตัดสินใจเรื่องนี้

payday ของเดือนหนึ่งจบวันที่ 2 ของเดือนถัดไป ส่วน double digit ของวันที่ 1.1 2.2 3.3 เริ่มก่อนวันจริง 3 วัน สองอันนี้จึงซ้อนกันทุกต้นปี

| โปร | ช่วง | ทับกับ |
|---|---|---|
| payday ธ.ค. | 24 ธ.ค. ถึง 2 ม.ค. | 1.1 (29 ธ.ค. ถึง 2 ม.ค.) |
| payday ม.ค. | 24 ม.ค. ถึง 2 ก.พ. | 2.2 (30 ม.ค. ถึง 3 ก.พ.) |
| payday ก.พ. | 24 ก.พ. ถึง 2 มี.ค. | 3.3 (28 ก.พ. ถึง 4 มี.ค.) |

กฎที่ตั้งไว้เป็นค่าตั้งต้น **โค้ดที่ลูกค้ากรอกคือโค้ดที่ได้** ระบบไม่สลับให้เอง ช่องกรอกมีช่องเดียว ใส่ได้ทีละโค้ด

เหตุผล ลิงก์โฆษณาแต่ละตัวพาโค้ดของตัวเองมาอยู่แล้ว คนที่กดลิงก์ payday ได้ 325 คนที่กดลิงก์ 1.1 ได้ 355 ไม่ต้องมีตรรกะเปรียบเทียบราคาให้พัง

ถ้าไอซ์อยากให้ระบบเลือกราคาถูกที่สุดให้อัตโนมัติเมื่อสองโปรทับกัน บอกได้ แต่ต้องเขียนเพิ่มและต้องอธิบายบนหน้าเว็บว่าทำไมราคาที่เห็นไม่ตรงกับโค้ดที่กรอก

## ข้อที่เหลือ ตัดสินแล้วทั้งหมด (11 พ.ย. 2569)

| เรื่อง | คำตอบไอซ์ |
|---|---|
| สลิปยอดไม่ตรง | ส่งเข้าหน้า review ให้ไอซ์กดเอง ไม่ปฏิเสธอัตโนมัติ ใช้ระบบ `review-order` ที่มีอยู่แล้ว |
| ผ่อนเวลาหลังหมดเขต | 6 ชั่วโมง ตรวจที่ server เท่านั้น |

ของแถมยังต้องรู้เพิ่มอีกข้อ คือจะใช้ชุดไหนเป็นชุดพิเศษ และจะส่งลิงก์แยกหรือรวมไปในอีเมลเดิม

# workflow การทำงาน

## สิ่งที่ได้จากการดูของจริงที่เพจ Diary Planner

เปิด `diaryplanners.com/dd/float1111?ref=fbads-1111` ดูแล้ว ของที่ลอกมาใช้ได้

- **ป๊อปอัพ** หัวสติ๊กเกอร์ "11.11 โปรวันคู่" ข้างในมีตั๋วใบเดียว ซ้ายคือส่วนลดเป็นจำนวนเงินตัวใหญ่ ขวาคือโค้ด ใต้ตั๋วบอกราคาหลังลดกับวันหมดเขต ปุ่มเดียวคือ "รับโค้ดส่วนลด" และมีบรรทัดเล็กว่า "กดเก็บโค้ด ลดให้อัตโนมัติตอนชำระเงิน"
- **หน้าแรกเปลี่ยนเป็นหน้าเทศกาล** มีสติ๊กเกอร์ 11.11 กับธงราว แล้วโชว์ราคาสามชั้น ลด 28% / 279฿ / ราคาร้าน 390฿
- **บรรทัดที่สำคัญที่สุด** คือ "ใส่โค้ด FLOAT1111 ให้แล้ว ลดเฉพาะชุดสไตล์ ถึง 12 พ.ย. 23:59 น." ประโยคเดียวบอกครบว่าไม่ต้องพิมพ์เอง ลดอะไร และหมดเมื่อไหร่ ของเราควรมีบรรทัดแบบนี้
- บอกส่วนลดทั้งเป็นเปอร์เซ็นต์และเป็นบาท และบอกเวลาหมดเขตเป็นชั่วโมงนาที ไม่ใช่แค่วันที่

ที่ลอกไม่ได้ เพจนั้นมีตะกร้ากับระบบล็อกอิน ส่วนลดจึงไปคิดตอน checkout ของเราไม่มีตะกร้า โค้ดต้องไปเติมให้ในหน้าสั่งซื้อแทน

4. หน้าหมดเขต (คนกดลิงก์เก่าหลังโปรจบ)
5. หน้ายังไม่เริ่ม (คนกดลิงก์ก่อนโปรเริ่ม)

ให้ไอซ์ดูก่อน อนุมัติแล้วค่อยเขียนโค้ด

### ขั้น 2 — ฝั่ง server ทำก่อนและ deploy ก่อน

1. ยุบราคาให้เหลือไฟล์กลางไฟล์เดียว ใช้ทั้งหน้าเว็บและ `verify-slip` ขั้นนี้ไม่เปลี่ยนพฤติกรรมอะไรเลย แค่ย้ายที่เก็บ
2. migration สร้าง `promo_codes` เพิ่มคอลัมน์ `promo_code` `ref` `expected_amount` ใน `orders` ตั้ง trigger ให้ DB เป็นคนใส่เวลา และใส่ `GRANT ... TO anon, authenticated, service_role;`
3. แก้ `verify-slip` ให้คำนวณยอดที่คาดหวังจาก pack บวกโค้ด ตรวจช่วงวันจากเวลาใน DB บวกผ่อนเวลา 6 ชั่วโมง และถ้ายอดไม่ตรงให้ส่งเข้า `review-order` แทนการปฏิเสธ
4. deploy `verify-slip` ขึ้น production

**ถ้าปล่อยหน้าเว็บก่อนขั้นนี้ สลิปราคาโปรทุกใบจะถูกปฏิเสธ**

### ขั้น 3 — ฝั่งหน้าเว็บ

1. เพิ่ม path `/dd/<โค้ดตัวเล็ก>` ในไฟล์ `_redirects` ชี้ไปหน้าแรก
2. หน้าแรกอ่านโค้ดจาก URL ตรวจกับ `promo_codes` ถ้าใช้ได้ก็เก็บลง localStorage แล้วแสดงป๊อปอัพ
3. หน้าแรกแบบเทศกาลแสดงเมื่อมีโค้ดใน localStorage และยังไม่หมดเขต หมดแล้วกลับเป็นปกติเอง
4. หน้าสั่งซื้อเติมโค้ดให้อัตโนมัติ แสดงราคาที่ลดแล้ว และมีช่องให้พิมพ์โค้ดเองได้สำหรับคนที่รู้โค้ดอยู่แล้ว
5. ราคาที่หน้าเว็บแสดงเป็นแค่การแสดงผล ตัวตัดสินจริงคือ server เสมอ

### ขั้น 4 — รายงาน

แก้ `daily-summary` และ `monthly-csv` ให้แยกยอดโปรออกมา ทั้งจำนวนออเดอร์ ยอดเงิน และแยกตาม `ref`

## กฎการมองเห็น ฉบับสุดท้าย (ไอซ์ 11 พ.ย. 2569)

ไอซ์: *"คนที่เข้าผ่านลิงก์สำหรับโปรโมชั่นเท่านั้นถึงจะเห็นราคาโปร คนเข้ามาเว็บธรรมดาก็เห็นราคาเต็มปกติ แยกกัน แค่คนที่เคยเข้าผ่านลิงก์ราคาโปรแล้วมาเข้าเว็บด้วยลิงก์ปกติก็จะเห็นราคาโปรเหมือนมันแคชไว้"*

และ *"ไม่เอาคำว่าโปรวันคู่เริ่ม xx ตอนนี้ยังเป็นราคาปกติ"*

มีสามกรณีเท่านั้น ไม่มีหน้าพิเศษอื่น

| ใคร | เห็นอะไร |
|---|---|
| กดลิงก์โปรในช่วงวันของโค้ด | ป๊อปอัพ แล้วหน้าแรกโหมดโปร 355฿ |
| เคยกดลิงก์โปรแล้ว เปิดเว็บด้วยลิงก์ปกติ ยังอยู่ในช่วงวัน | หน้าแรกโหมดโปร 355฿ เพราะเครื่องจำโค้ดไว้ |
| คนอื่นทั้งหมด รวมคนที่กดลิงก์โปรนอกช่วงวัน | หน้าแรกปกติ 499฿ ไม่มีแถบ ไม่มีป๊อปอัพ ไม่มีคำว่าโปรที่ไหนเลย |

**ไม่มีหน้า "ยังไม่เริ่ม" และไม่มีหน้า "หมดเขตแล้ว"** ทั้งสองกรณีคือกรณีที่สามในตาราง คือหน้าแรกปกติเฉยๆ เหตุผลคือไม่ประกาศให้คนที่พร้อมซื้อวันนี้รู้ว่ามีโปรแล้วหยุดรอ

ผลที่ตามมาที่ต้องระวัง ถ้าแอดเริ่มยิงก่อนวันที่โค้ดมีผล คนที่กดเข้ามาจะเห็น 499฿ โดยไม่มีคำอธิบาย **ต้องตั้งเวลาเริ่มแอดให้ตรงกับ `starts_at` ของโค้ดเสมอ**

## ความคืบหน้าขั้น 2 (11 พ.ย. 2569)

| งาน | สถานะ |
|---|---|
| migration `promo_codes` + คอลัมน์ใน `orders` | ✅ apply ขึ้น production แล้ว (เพิ่มของใหม่ล้วน ไม่แตะของเดิม) |
| seed โค้ด `DECK1111` 355฿ (8 ถึง 12 พ.ย.) และ `PITCHNOV` 325฿ (24 พ.ย. ถึง 2 ธ.ค.) | ✅ |
| `review-order` อ่าน `expected_amount` | ✅ deploy แล้ว (v4) ออเดอร์เดิมค่าเป็น null ตกกลับราคาแพ็กเหมือนเดิม |
| `verify-slip` รับราคาตามโค้ด + ผ่อนเวลา 6 ชม. + ยอดไม่ตรงเข้า review | ✅ deploy แล้วผ่าน Supabase CLI (`npx supabase functions deploy verify-slip --remote=... --yes`) |
| `_redirects` `/dd/` + ป๊อปอัพ + หน้าแรกโหมดโปร + หน้าสั่งซื้อ | ยังไม่เริ่ม (ขั้น 3) |

### การตัดสินใจที่ต่างจากแผนเดิม พร้อมเหตุผล

1. **ไม่ทำ trigger ใส่ `created_at`** ใช้เวลาที่ server ตอนตรวจสลิปแทน ปลอมไม่ได้เหมือนกันแต่ไม่ต้องแตะ trigger ของตาราง `orders` ที่ใช้ขายอยู่ และไม่พังเคสออเดอร์ที่ไอซ์ตั้งวันย้อนหลังเอง (ออเดอร์เทสต์)
2. **ตารางเก็บ `discount_price` ราคาสุทธิ ไม่เก็บ percent** ของเราลดเป็นราคาตายตัว 355 กับ 325 เก็บเลขเดียวจบ ไม่มีปัญหาปัดเศษ และเลขในตารางคือเลขเดียวกับที่โชว์บนเว็บและเทียบกับสลิป
3. **ไม่มี `max_uses` / `applies_to_pack`** โค้ดคุมด้วยช่วงวันอยู่แล้ว และลดเฉพาะแพ็ก 1 สิทธิ์ตายตัว ถ้าวันหนึ่งอยากจำกัดจำนวนครั้งบอกได้ ค่อยเพิ่ม
4. **ยังไม่ยุบไฟล์ราคา** ราคาโปรอยู่ในตาราง `promo_codes` ที่เดียว ส่วนราคาเต็มยังอยู่สองที่เท่าเดิม (หน้าเว็บกับ edge function) การยุบต้องเพิ่ม build step ซึ่งแลกไม่คุ้ม

### ผลทดสอบราคาบน production 11 พ.ย. 2569

สร้างออเดอร์ทดสอบ 4 ใบ (ref_source `internal_test`, slip_url ปลอม) ยิงเข้า `verify-slip` จริง แล้วอ่าน `expected_amount` ที่ server คำนวณ ลบออเดอร์ทดสอบทิ้งแล้วทั้งหมด ไม่มีอีเมลออก ไม่เรียก Slip2Go เพราะตกที่ขั้นอ่านสลิป

| ออเดอร์ | ยอดที่ server คาดหวัง | ถูกไหม |
|---|---|---|
| แพ็ก 1 โค้ด DECK1111 | 355 | ✅ |
| แพ็ก 1 ไม่มีโค้ด | 499 | ✅ |
| แพ็ก 1 โค้ด PITCHNOV (ยังไม่ถึงวันเริ่ม 24 พ.ย.) | 499 | ✅ ตกกลับราคาเต็มเอง |
| แพ็ก 5 โค้ด DECK1111 | 1,990 | ✅ โค้ดไม่แตะแพ็กทีม |

แปลว่าตอนนี้สลิป 355฿ ที่มาพร้อมโค้ด DECK1111 จะถูกส่งให้ Slip2Go ตรวจที่ยอด 355 ไม่ใช่ 499 แล้ว
